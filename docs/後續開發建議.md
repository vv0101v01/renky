# 後續開發建議（v0.1.2）

> 版號標示沿用分支名 `v0.1.2`，不另立版號。
> 前提：現行 v0.1.2 已把警告清乾淨（預設 0；`--warn-list "+all"` **全部提示**亦為 0），
> 且目錄 239/239、實例 46,179、取樣政策 134/0 全數通過。
> 因此本文件不再談「修警告」，而談**如何把這個狀態鎖住、以及下一步的槓桿在哪**。

---

## 1.（最高優先）把「0 warning ＋ 234 通過」變成不可回退的 CI 閘門

目前這些數字只存在於開發者手動執行；任何一次提交都可能悄悄回退。
建議新增 `.github/workflows/ci.yml`（社群 Action：`hustcer/setup-moonbit@v1`）：

```yaml
name: CI
on: [push, pull_request]
jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hustcer/setup-moonbit@v1
      - name: 工具鏈版本（回溯用）
        run: moon version --all
      - name: 1. 型別檢查（全目標、嚴格）
        run: moon check --target all --deny-warn
      - name: 2. 嚴格型檢查（全部提示）
        run: moon check --target all --warn-list "+all" --deny-warn
      - name: 3. 目錄迴歸（239/239、46,179 實例、政策 134/0）
        run: moon test
      - name: 4. 生成器可重現（N-45）
        run: moon run cmd/genoblig | diff - oblig_auto.mbt
      - name: 5. 全庫自證判準
        run: moon run cmd/main | grep -qE "全部義務通過：[0-9]+/[0-9]+，無未決條目"
      - name: 6. 格式化（oblig_auto.mbt 為生成檔，例外）
        run: |
          if moon check --fmt 2>&1 | grep "File not formatted" | grep -v oblig_auto.mbt | grep -q .; then
            moon check --fmt; exit 1
          fi
```

要點：

- **釘住工具鏈**：MoonBit 演進快（0.10.4 才新增 `extend` 並棄用隱式方法推廣；
  0.10.14 起 E0079 已預設開啟）。建議在 CI 記錄 `moon version --all`，
  必要時把 `version` 固定成已知良好版本，避免「昨天綠、今天紅」。
- 第 2 道閘門是 MoonBit 工具鏈目前的最強形式：**全部提示零警告**（`+all` 已含 `unnecessary_annotation`）。
- 建議另開一支 `daily` workflow：`moon upgrade` 後跑同樣六道閘門，提早看到新版本帶來的新警告。

## 2.（本週）合規與可發佈性

| 項目 | 現況 | 建議 |
| --- | --- | --- |
| `LICENSE` | **缺檔**（`moon.mod` 已宣告 Apache-2.0） | 補 Apache-2.0 全文 |
| `repository` | 空字串 | 填 `https://github.com/vv0101v01/renky` |
| `CHANGELOG.md` | 無 | 由 v0.1.0 起補記；警告清理併入 v0.1.2 之記錄 |
| 公共介面 | 無 `.mbti` 入庫 | `moon info` 產出 `pkg.generated.mbti` 入庫，CI 檢介面漂移 |
| 發佈 | 未上架 | `moon login` 後 `moon publish`（`axiom/hilbert` 之名稱需 "axiom" 帳號；否則改用 `<帳號>/hilbert`） |

`.mbti` 值得入庫的理由：本庫已在 `Q`／`Cpx` 掛了 `#deprecated` 的 `extend`（為下游相容而保留），
介面快照能讓「哪些方法屬公共 API、哪些只是歷史殘留」一眼可見，也讓 semver 有依據。

## 3.（本週）解開「生成物 × 格式化」的張力

現況（本次已處理）：`oblig_auto.mbt` 由 `cmd/genoblig` 生成，其逐位元組可重現性是義務，
因此它**刻意不套用 `moon fmt`**。長期解法是讓生成器輸出即為格式化正則形式：

- **方案 A（推薦）**：在 `cmd/genoblig` 的排版器裡採用 `moon fmt` 之規則
  （`match` 分支換行、`if` 單行化、尾逗號、行寬），之後 `oblig_auto.mbt` 入庫前不必再 fmt，
  六道閘門中的第 6 道即可移除例外。
- **方案 B（過渡）**：CI 改為「生成 → 於包內 `moon fmt <暫存檔>` → 比較」。
- 不建議反向（把生成檔格式化後改比對格式化版）：那會讓「逐位元組」的義務退化成「語意相同」，
  而位元組級一致正是本庫一貫的鑑別力來源。

## 4.（中期最有價值）接上 `moon prove`：把 12 條 proof 標註變成真證明

本次清理順手補上的 12 個迴圈 `where { proof_invariant / proof_reasoning }`，
目前只是**語法合格**（編譯器認得、不再報 E0038/E0039），並未被任何求解器檢查。
這正是本專案最自然的下一步——把「可執行之義務自證」升級為「為什麼3 可證」。

實測（本機，安裝 `z3` 後）：

```text
$ moon prove          # 未開 proof 之套件：無輸出
$ # moon.pkg 加 options("proof-enabled": true) 後：
t/proof
  Succeeded: 0 goals proved
  1 of 1 packages proved
```

**要有效果必須有契約**：無 `proof_require`／`proof_ensure` 之函式不生成目標；
邏輯側謂詞要放在 `.mbtp` 檔（Why3 由工具鏈內建，求解器需自備 z3／cvc5／alt-ergo 之一）。

建議路線（由小到大，且維持本庫「誠實」風格）：

1. 開 `proof-spike` 分支：`moon.pkg` 加 `options("proof-enabled": true)`，
   挑 **kernel.mbt 之 `sqrt_newton`**（殘差界 → 後向誤差）、**`big_sqrt_exact`**、
   **fp.mbt 之 `normmod`**（值域不變量）三處，各寫 `.mbtp` 引理與契約。
2. 能被證的就證，證不出來的明確列為「未證」——與 K/L/M 管「保留誠實反例」同一哲學。
3. 成熟後把 `moon prove` 加進 CI（參考 `moonbit-community/verified` 的 `.github/why3.conf`：
   Alt-Ergo + Z3 + CVC5 多求解器互補）。

> 提醒：`moon prove` 的失敗多半是 *timeout*（求解器逾時），不等於「命題為假」；
> 報表上必須區分這兩者，才符合本庫對精確性的要求。

## 5. 數學與加速層的續進

- **N 群**：`docs/N群第四輪擴展計劃.md` 已有清單，照表推進即可；本次警告清理未動任何算式，
  故指紋不受影響，N 群之「既有指紋一位元未變」承諾仍成立。
- **加速層新管線**（K/L/M 之縱深）：現行是「多模 𝔽p → CRT → 有理重建」。
  可考慮再加兩條並列路徑並以 `Cost` 模型實測分派：
  - ℤ[x] gcd：**subresultant PRS**（免內容爆炸）與 **Hensel 提升**（p-adic，逐位提升）；
  - 𝔽p[x] 乘法：**NTT**（現有 `fpp_*` 為學校法；`realmat.mbt` 已有 FFT 可借鏡）。
  兩者都要附「正向性自證」與誠實反例（本庫既有格式）。
- **誠實反例台帳**：把 `accelscan` 之拒絕案例（如 `zpoly_from_roots_linear` ×0.60）
  固定成一張表、每版輸出，避免後人重踩；亦可作為「分派器正確拒絕」之證據鏈。
- **備忘錄不變量**：N-77 已指出「無差別備忘會讓 N-62 兩條主張退化成恆真」；
  建議把「繞過條件」寫成機器可檢斷言（本庫已有先例可循）。

## 6. 量測、回歸與開發迴路

- **固定 profile**：`docs/逐條量測.tsv` 與 `cmd/audit` 之掛鐘數字必須標明 build profile
  （debug／release），否則跨版本不可比。建議 README 註明，並在 CI 產出「本次 vs 上次」對照。
- **開發迴路**：全庫自證約 105 秒。建議 `cmd/main` 支援 `--only <前綴>`（如只跑 K/L/M 或某群），
  讓日常迭代不必每次等兩分鐘；完整跑留給 CI 與發版。
- **覆蓋率**：`moon coverage analyze` 產生報告並入 `docs/`（本庫義務密度高，覆蓋率應接近滿）。
- **性質測試**：官方 `moonbitlang/quickcheck` 可作為「獨立於自證義務」的第二意見來源。
  若要維持「零第三方依賴」之宣言，把它放在獨立 package（不進函式庫本體），或僅在 CI 內實驗。

## 7. 文件與對外敘事

- README 首段「`moon check` 0 error 0 warning」旁，補上可複製的驗證指令
  （含最強閘門 `--warn-list "+all" --deny-warn`）。
- 新增 **`docs/警告政策.md`**（或把 `docs/警告清理報告.md` §4 抽出成常設文件）：
  說明 `extend`／`#deprecated` 之掛載政策，以及**結構字面值之定案寫法**
  `let vs = T::{ … }`（不再重複 `let` 型別標註，使 E0084 與 E0073 同時成立）。
  這是給未來貢獻者（與未來的自己）的行為契約。
- 若上架 Mooncakes，README 加 `moon add <帳號>/hilbert` 片段與三個最小示例
  （ℚ 矩陣求逆、Λ² 楔積、四元數旋轉各一）。

## 8. 風險清單

| 風險 | 說明 | 對策 |
| --- | --- | --- |
| 工具鏈漂移 | `implicit_impl_as_method` 下一版預設開啟；`extend` 將由軟關鍵字轉真關鍵字 | CI 記錄版本；勿以 `extend` 作變數名；用 daily workflow 預警 |
| 寫法慣例 | 若有人寫回 `let x : T = T::{…}`（觸發 E0073）或 `let x : T = {…}`（觸發 E0084），閘門即紅 | 慣例寫進 `moon.mod` 註解、`docs/警告政策.md` 與 CI 訊息；`+all` 閘門會直接指出位置 |
| `#deprecated` 掛載 | 下游若廣用 `q.s_add(...)` 會收到遷移提示 | 於 CHANGELOG 說明；語言最終移除推廣時直接刪除該 extend |
| 單包 100 檔 | 目前 check ~4s、test ~105s，尚可 | 暫不拆；若拆，須同步 README「零 import」宣言與指紋驗證 |
| 生成物過時 | `oblig_auto.mbt` 與生成器不同步即破壞 N-45 | 已納入 CI 第 4 道閘門 |

## 9. 一週行動清單（可直接照做）

1. 貼上 §1 的 CI workflow（六道閘門）。
2. 補 `LICENSE`、`repository`、`CHANGELOG.md`；`moon info` 產生 `.mbti` 入庫。
3. 生成器 fmt 正則化（§3 方案 A）——完成後第 6 道閘門可刪。
4. 開 `proof-spike`：裝 z3、`options("proof-enabled": true)`、從 `sqrt_newton` 試證（§4）。
5. 在 `cmd/main` 加 `--only` 子集模式，讓開發迴路從 105 秒降到數秒（§6）。
