# 專案健檢與規劃（手寫；統計部分見 `docs/專案審計.md`）

## 七、本次健檢所發現並修復的問題

### 7.1 分層違規 47 處（已量出，未全修）

把程式碼按 `space → acce → comb → oblig → 目錄` 分層之後，
量到 **47 處低層引用高層**：

```text
  comb  → oblig   22 處   tri.mbt 引用 ob_a02/ob_b01/…（字母群表）
                          nlaw/autoob/compose/comb21/comb7scan 引用
                          qr、samples、maxi —— 這三個是**測試輔助函式**
                          卻定義在 oblig_core.mbt / oblig_space.mbt
  space → comb     9 處   spacereg2 引用 CombRec/comb7_registry；
                          spacereg 引用 SpaceExpr、str_hash64
  acce  → comb     7 處   ncrt/accel/accelfix 引用 nlaw.mbt 的
                          compound、qpow_fast、qblock_diag、tmat
  acce  → oblig    7 處   accel/accelfix2/accelscan 引用 ob_rng、qmat、zrand
  space → acce     1 處   spacereg2 引用 spd_fast（第十八輪刻意接的）
```

**最值得記的一條**：`qr`、`ob_rng`、`qmat`、`samples`、`maxi`、`zrand`
是隨機與取樣輔助，它們住在 `oblig_*.mbt` 裡，卻被**函式庫本體**使用。
這不是風格問題，是分層反轉 —— 函式庫依賴它的測試層。

### 7.2 重複

```text
  逐字相同之函式本體（長度 > 120）      0 組
  改名後相同（長度 > 200）              6 組
```

六組全部是**正當的對偶實作**，不是複製貼上：
`fpp_add`／`fpp_sub`、`column_space`／`row_space`、
`sub_scan`／`ek_scan`、`sub_digest`／`ek_digest`、
`op_digest`／`uni_digest`、`rcompose_confusion_syn`／`_dom`。
保留。

### 7.3 死碼 64 個 pub fn（已隔離 57 個）

全專案從未被呼叫的公開函式 64 個（私有函式 0 個）。
依使用者既有指示「不得刪除，可隔離」，移入三個隔離區套件：

```text
  space/attic.mbt   22 個
  acce/attic.mbt    13 個
  comb/attic.mbt    22 個
  留在原處          7 個    依賴主套件私有內部，移出需擴大公開介面
                            （charge_reduce_rows、g_trimemo 欄位、
                             law_cache 等），不值得為了放備品而開放
```

隔離區是獨立套件 `axiom/hilbert/<area>`，**單向依賴主套件**。
這個方向很重要：主套件不引用隔離區，所以移進去**不可能破壞任何
既有結果** —— 真有人在用，編譯會當場失敗。這是「安全地放著」的唯一寫法。

### 7.4 為什麼沒有把全部程式碼搬進四個資料夾

MoonBit 的套件單位是**目錄**：子目錄若無 `moon.pkg` 則不屬於任何套件
（已實測：放一個函式進去，根套件看不到它，E4021 未繫結）。
所以「開四個資料夾」等於「切成四個套件」，而那需要：

```text
  跨套件識別字出現次數      7,396 處   全部要加 @space. / @acce. / … 前綴
  需先破除之分層違規          47 處   含 tri.mbt → 目錄義務的真環
```

7,396 處機械替換，而本庫有 11 個釘死的指紋與 264 條義務 ——
一次替換錯一個符號就可能靜默改掉某個指紋。
**我沒有在沒有確認的情況下做這件事。**
已完成的是讓它**變可行**的前置：死碼移出（主套件公開介面縮小 57 個符號）、
分層違規量化成一張可檢查的清單。

## 八、評分

覆蓋分（對照＋成本＋定理＋反例，滿分 4）只用來找「連形式都缺」的條目。
**它不是品質分**：四項都寫了但內容空洞一樣拿滿分。

最該讀的一行是群組表裡的這個落差：

```text
  A–J（基礎 140 條）   有對照 0 條
  K/L/M（加速 28 條）  有對照 4 條
  N（結構律 96 條）    有對照 57 條
```

A–J 是最早寫的 140 條，而兩側對照的紀律是第十輪以後才立起來的。
**它們不是「驗得淺」—— 它們的義務確實在跑、確實在比對；
缺的是「錯的版本會不會被抓到」這一層。**
這是全專案目前最大的單一品質缺口，也是下一步最該補的東西。

## 九、規劃（依投入產出排序）

```text
  1. A–J 補兩側對照          140 條，缺口最大，且每條成本低（既有義務加一個錯式）
  2. 修分層違規              47 處；先把 qr/ob_rng/qmat/samples 移到基礎層
  3. 破 tri.mbt → 目錄義務環  改成依賴注入（表由呼叫端傳入）
  4. 切四個套件              前三項做完後才可行；7,396 處前綴應以腳本分批、
                             每批跑完八道閘門並比對 11 個指紋
  5. N-86（12.6 s）仍是最貴   k3 段 1,495 次 ℚ 行列式，可換 CRT
```

第 1 項與第 4 項的關係值得說清楚：**切套件是整理，補對照是驗證**。
前者讓人讀得舒服，後者決定這個庫說的話算不算數。先做第 1 項。
