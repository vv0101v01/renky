# 形式驗證接入評估（`moon prove` × `axiom/hilbert`）

> 結論先講：**管線可用，主套件現階段不可接入**。
> 純 `Int`／`Bool` 之函式與迴圈可被降低並自動證明；本庫主套件因
> `Array` 欄位與 core `BigInt` 之 WhyML 降低缺口而**在生成階段即失敗**。
> 因此 `moon prove` 暫不進 CI 閘門（見 §5）。

---

## 1. 環境

| 項目 | 版本／來源 |
| --- | --- |
| 工具鏈 | `moon 0.1.20260920`／`moonc v0.10.14+7d59c7ec9` |
| Why3 | 工具鏈內建（`~/.moon/lib/why3`，`moon prove` 直接驅動其 `why3server`，無需另裝 `why3` 執行檔） |
| 求解器 | 自備，`moon prove` 會搜尋 `z3`／`cvc5`／`alt-ergo`；本次用 z3 4.13.3 |
| 啟用方式 | 於**目標套件**之 `moon.pkg` 加 `options("proof-enabled": true)` |
| 契約語法 | `fn f(...) -> T where { proof_require: …; proof_ensure: result => … }`；迴圈 `} where { proof_invariant: …; proof_reasoning: (#| …) }`；邏輯側謂詞與引理放 `.mbtp` |

無契約之函式**不生成證明目標**（實測：`moon prove` 回報 `0 goals proved` 且不報錯）。

## 2. 實測 A — 最小例子（通過 ✔）

```moonbit
///|
/// 加一（帶契約）。
pub fn inc(x : Int) -> Int where {
  proof_ensure: result => result == x + 1,
} {
  x + 1
}

///|
/// 迴圈累加 0..n（帶不變量與契約）。
pub fn sum_to(n : Int) -> Int where {
  proof_require: n >= 0,
  proof_ensure: result => result >= 0,
} {
  let mut s = 0
  for i = 0; i < n; i = i + 1 {
    s = s + i
  } where {
    proof_invariant: s >= 0,
    proof_invariant: i >= 0,
    proof_invariant: i <= n,
    proof_reasoning: (
      #| i 單調遞增，s 每步增加非負項。
    ),
  }
  s
}
```

```console
$ moon prove
t/ctr
  Succeeded: 2 goals proved

Summary:
  1 of 1 packages proved
  2 goals proved
```

要點：編譯器會為迴圈**自動生成 variant**（本例為 `n − i`）與 invariant 子句，
`proof_ensure`／`proof_require` 落為 `ensures`／`requires`。
這說明「本庫已寫下的 12 處 `proof_invariant`／`proof_reasoning` 標註」在語言層是**真語法**，
只是尚未被任何求解器檢查。

## 3. 實測 B — 主套件（失敗 ✘）

```console
$ # 副本之 moon.pkg 加 options("proof-enabled": true)
$ moon prove
"/tmp/proofspike/_build/verif/pkg_5_axiom_7_hilbert.mlw", line 24, characters 57-62:
  unbound type symbol 'array'
```

診斷（證據為生成之 WhyML）：

```whyml
type axiom_hilbert__mat 'f = {
    axiom_hilbert__Mat__mrows : Moonbit_builtin_prelude_Int.t;
    axiom_hilbert__Mat__mcols : Moonbit_builtin_prelude_Int.t;
    axiom_hilbert__Mat__data  : array 'f        (* ← 'array' 未引入 *)
  }
...
  type axiom_hilbert__q = {
      axiom_hilbert__Q__num : _moonbitlang_core_bigint_BigInt;  (* ← core 型別亦無引入 *)
      axiom_hilbert__Q__den : _moonbitlang_core_bigint_BigInt
    }
```

- `Mat[F]` 之 `Array[F]` 欄位被降低為 `array 'f`，但生成檔未 `use array.Array`（或等價）
  ⇒ Why3 於**型別檢查階段**即報 `unbound type symbol 'array'`。
- `Q` 之 `BigInt` 欄位引用 `_moonbitlang_core_bigint_BigInt`，同理無對應 theory 引入。
- 這兩個缺口是本庫的**結構性**特徵（矩陣、ℚ 是本庫的地基），不是個別函式的問題。

## 4. 若要接入：建議路線（由小到大）

1. **可證子集**：以「純 `Int`／`Bool`／`Double` 摘要」的核心為試點，例如
   `kernel.mbt` 之迭代終止性與界、`crt.mbt` 之模數不足判定、
   `policy.mbt` 之 trial_floor 記帳一致性。**不要**一開始就碰 `Mat`／`Q`。
2. **邏輯側**：謂詞與引理放 `.mbtp`（`.mbt` 只留契約），以 `proof_axiomatized` 誠實標記未證公理。
3. **獨立 package**：把試點放在 `verif/` 或其他 package，主樹 `moon.pkg` **不開** `proof-enabled`，
   確保 `moon check`／`moon test`／自證耗時與指紋皆不受影響。
4. **求解器策略**：CI 若要跑，需自備 `z3`（或 `cvc5`／`alt-ergo`），並以 `--why3-config` 給出多求解器策略；
   參考 `moonbit-community/verified` 之 `.github/why3.conf`。
5. **誠實回報**：`moon prove` 之失敗多為 *timeout*（求解器逾時），
   與「命題為假」不同，報表必須分開陳述。
6. **追蹤工具鏈**：`array`／`BigInt` 之 lowering 缺口屬上游問題；
   以 `.github/workflows/toolchain-drift.yml` 之外再偶爾複跑 §3 之重現指令即可得知是否已修。

## 5. 對本庫閘門之影響：無

`moon prove` **不進** `.github/workflows/ci.yml`：
現階段它對本庫唯一的可證對象（純 Int 子集）尚未切出，強行納入只會產生
「0 goals proved」的假綠燈或 timeout 的假紅燈，兩者都違反本庫「誠實」原則。
待 §4 之試點產生真目標後，再以獨立 workflow 加入。
